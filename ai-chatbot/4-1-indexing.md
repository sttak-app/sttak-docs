# CB-4-1. 구현 설계 — 색인 파이프라인 (결정 항목 카탈로그)

> 구체 구현 확정본이 아니라 **"이것들을 정해서 채워 넣는다"** 목록이다. 각 항목은
> 결정 → 본 문서 갱신 → (필요 시) ADR 기록 순으로 확정한다.

## CB-4-1.1 청크 분할 — 정할 것

우리 데이터는 기사당 300~600자(≈150~350토큰)라 **크기 분할이 아니라 의미 단위 분할** 문제다.
토큰 단위(1k/10k) 분할은 비채택 — 그 크기면 자르는 게 아니라 여러 기사를 한 청크에 합치게 되어
출처 역참조·종목 필터·벡터 순도가 전부 깨진다. 토큰 한도가 걸리는 지점은 임베딩 입력 상한
(8,191토큰 — 여유 충분)과 프롬프트 총량(top-N 으로 제어)뿐. 단 원문 전문이 입력에 들어오는
날(크롤링 재론 시)에는 기사당 수천 토큰이 되므로 토큰 기반 분할을 재론한다.

| 후보 | 내용 | 평가 관점 |
| --- | --- | --- |
| A. 1기사=1청크 (현행) | 요약+판단 합본 | 단순, 의도 섞임 |
| **C. 요약 청크 + 종목판단 청크** (권장안) | 기사당 1 + 종목당 1 | 질문 의도("무슨 일" vs "내 종목엔")와 1:1, stock_codes 필터와 정합. 판단 청크의 짧음은 컨텍스트가 보완 |

- ❓ 확정은 평가셋 A/B (특히 "○○ 왜 호재?" 유형에서 차이 예상)
- 용어(TERM)는 1용어=1청크 유지, 컨텍스트 생성 제외(자기완결적)
- 청크 종류가 늘면 (원천 타입, 원천 ID) 유니크 체계 재설계 (NEWS_SUMMARY / NEWS_STOCK / TERM 류)

## CB-4-1.2 컨텍스트 생성 — 정할 것

- **프롬프트 초안 v1** (Anthropic Contextual Retrieval 원형을 우리 도메인·한글로 번안 —
  실측 검증 후 확정, C-NFR8):

  ```
  <기사>
  제목: {원문 제목}
  발행일: {published_at, YYYY-MM-DD}
  관련 종목: {종목명(종목코드), …}
  본문: {원문 스니펫}
  </기사>

  아래는 위 기사에서 만들어진 청크다.

  <청크>
  {청크 내용 — 요약 청크 또는 종목판단 청크}
  </청크>

  이 청크가 전체 기사 속에서 어떤 위치인지(언제, 어떤 종목에 대한, 무슨 사건의 어떤 부분인지)
  짧고 간결한 맥락 한두 문장으로 작성하라. 목적은 이 청크의 검색(어휘·의미 매칭) 향상이다 —
  종목명·날짜·핵심 사건명을 반드시 명시하고, 기사에 없는 사실은 넣지 않는다.
  맥락 문장만 출력하고 다른 말은 하지 않는다.
  ```

  - 설계 의도: ① `<기사>`/`<청크>` 태그 = 데이터 펜싱 ② 기사 블록을 앞에 고정 배치 —
    같은 기사의 청크 여러 개(요약+종목판단)를 이어 생성할 때 프롬프트 캐시 적중 ③ "종목명·
    날짜·사건명 명시"가 BM25 직격 조항 ④ 원형의 "Answer only with the succinct context" 를
    "맥락 문장만 출력" 으로 유지 (후처리 파싱 불요)
- 입력: 기사 제목+스니펫 + 청크 / 출력: 50~100토큰 / 모델: luna
- 실행 위치: 임베딩 스텝 선행 단계, 멱등(context 없음 대상), 실패 시 해당 청크만 다음 회차
- 비용: 우리 물량(일 ~185기사)에서 일 수 센트 수준 — 백필 1회성 별도

## CB-4-1.3 스키마 — 정할 것

**PG 청크 테이블** (신규 마이그레이션):
- 확정 골격: chunk_id PK, 원천 참조(news_id 또는 타입+ID), raw_text, context, 시각
- **embedding 컬럼 보관 확정 (9/19)** — vector(3072, large). ES 유실·매핑 변경·전량 재색인 때
  재임베딩 비용 없이 PG 만으로 복구(C-NFR2 원칙의 완성). 임베딩 배치가 PG 에 쓰고, 색인
  스텝은 PG 값을 그대로 ES 로 복사
- 기존 knowledge_chunk: **신규 테이블 백필 검증 후 DROP 확정 (9/19)** — 듀얼런 폴백은 신규 테이블 기반 pgvector 검색(HNSW)이 담당, 구 테이블 유지 불필요

**ES 인덱스** (노션 안 + 보강):
- search_text(nori — **context+raw_text+원문 제목·스니펫 합본**), embedding(dense_vector,
  cosine, dims 3072 — large 확정), raw_text(표시용), **stock_codes(keyword — 보강)**, published_at(date),
  source_type(NEWS_SUMMARY/NEWS_STOCK/TERM — **뉴스·용어 한 인덱스 통합**, 4-2 확정 9/19. 퀴즈만 후속 별도 인덱스), _id=chunk_id
- **alias 로만 접근** (`chunk-v1` → alias) — 매핑 변경·전량 재색인 무중단
- nori 상세는 **결정 사항이 아니라 고려 사항** — 기본 설정으로 시작하고, 샘플 토큰화 검증에서 문제가 관찰될 때만 도입을 검토: 분해 모드 조정, 사용자 사전(종목명·"따상" 등), 동의어 사전(엔솔↔에너지솔루션). 평가셋 결과가 도입 여부의 근거

## CB-4-1.4 임베딩 — 정할 것

- **모델 확정: text-embedding-3-large(3072)** (C-NFR4, 9/19) — ADR-018 supersede 로 기록.
  퀴즈 유사도는 small 유지(이원화). ES dims=3072
- 임베딩 대상 = 검색 필드와 동일한 **합본**(컨텍스추얼 임베딩)
- 문서에 임베딩 모델 버전 필드 기록 (후일 교체 추적)
- 백필: 기존 청크 전량 = 컨텍스트 생성 + 재임베딩 + 색인 — ES 이관 배치에 묶어 1회

## CB-4-1.5 색인 배치 — 정할 것

- 실행 시점: 가공(ENRICHED) 후속 — **기존 임베딩 배치를 확장한다 (확정 9/19)**: 스텝 구성을 [컨텍스트 생성 → 임베딩(신규 테이블) → ES 색인] 으로 재편. 신설 잡 없음 — 스케줄·트리거(Jenkins)·관측 배선 재사용
- 멱등 규칙: PG 기준 anti-join / 재색인(전량) 절차: 새 인덱스 생성 → 색인 → alias 스위치
- term 갱신 전파 경로 (upsert 감지 → 재생성)
