# CB-5-1. 테스트 (챗봇 + 뉴스 AI)

테스트 원칙은 `../ai-feature/5-1`과 같다. **테스트에서는 실제 LLM이나 검색 엔진을 호출하지
않고, 판단 로직은 실제 코드로 검증한다.** 검색과 답변의 품질은 평가(`4-4`)에서 확인하고,
테스트는 이미 구현된 동작이 깨지는 것을 막는 데 집중한다.

## CB-5-1.1 레이어별 대상

| 대상 | 방식 | 검증하는 것 |
| --- | --- | --- |
| RRF 융합 | 순수 함수 | 순위 시나리오 고정 검증 |
| 검색 질의 조립 | 검색 클라이언트 목 | kNN의 k=30·cosine, BM25 대상 필드(`search_text`), 공통 필터(`stock_codes`·7일)의 pre-filter 적용, 용어 청크의 기간 예외, RRF 입력 구성을 검증한다. 필드 순서나 검색 엔진 버전에 따라 쉽게 깨질 수 있는 전체 질의 스냅샷은 비교하지 않는다. 전체 질의의 동작은 E2E 테스트에서 확인한다 |
| rerank | LLM 목 | 청크의 통과·탈락 반영, 판정 불능 시 전체 통과, 결과가 없을 때 C-FR6 경로 진입 |
| 프롬프트 조립 | 검색 포트 목 | 통과한 청크 수에 따른 저근거 지시, 결과가 없을 때 [참고 자료] 영역과 출처가 비어 있는지, NEWS 승격이 포함되는지 확인한다 |
| 출처 구성 | 순수 함수 | 프롬프트에 넣은 `document`의 원문 URL만으로 출처를 만드는지 확인한다(`3-2` 원칙 6) |
| 뉴스 가공 | LLM 목 + 페이크 검증기 | 요약·판단의 독립 실행과 결과 병합, 한쪽 실패 시 기사 전체 실패, 판단 라벨 변경 시 반려 |
| 색인 단계 | 목 | 이미 색인한 데이터 건너뛰기, 실패한 건만 분리 처리 |
| 색인·검색 E2E | 검색 엔진 컨테이너(도입 시) | 시드 데이터를 색인한 뒤 하이브리드 질의가 동작하는지 대표 시나리오 몇 개로 확인한다. 기본 Elasticsearch 이미지에는 nori가 없으므로 nori가 포함된 OpenSearch 공식 이미지나 별도 이미지를 사용한다. 컨테이너를 시작하는 데 수십 초가 걸리고 1GB 이상의 메모리가 필요하므로 색인·검색 테스트만 태그로 분리해 선택적으로 실행하는 방안도 검토한다 |
| 듀얼런 스위치 | 설정별 컨텍스트 | `sttak.rag.store` 값에 맞는 검색 구현이 선택되는지 확인해 전환 과정의 문제를 막는다 |

## CB-5-1.2 반드시 있어야 하는 것

1. **자료가 적거나 없는 경우**: 자료가 적다는 안내가 프롬프트에 추가되는지, 검색 결과가
   없을 때 출처가 빈 목록인지 확인한다. "자료가 없다"고 단정하거나 답변을 거부하지 않아야
   하며, 용어 질문도 같은 이유로 거부해서는 안 된다.
2. **원문 URL 유지**: 검색 결과가 rerank와 프롬프트 조립을 지나도 `document`의 원문 URL이
   유지되는지 확인한다. 중간 단계에서 URL이 빠지면 최종 출처를 만들 수 없다.
3. **검증 우회 방지**: 검수를 통과하지 않은 답변이 전송 단계에 도달할 수 없는지 확인한다.
4. **검색 결과가 없는 경우의 분기**: 한쪽 검색에만 결과가 있으면 RRF를 생략하고 해당 결과가
   rerank로 넘어가는지 확인한다. 양쪽 모두 결과가 없으면 rerank를 호출하지 않아야 한다.
   이때 NEWS 승격 청크가 있으면 참고 자료로 사용하고, 없으면 일반 지식 답변을 생성하는지도
   확인한다. 어느 경우에도 결과가 없다는 이유로 오류가 발생해서는 안 된다(`4-2`).

## CB-5-1.3 하지 않는 것

- 실제 검색 클러스터나 LLM을 호출하지 않는다. 비용이 들고 결과가 매번 달라질 수 있다.
- 어떤 청크가 상위에 나오는지 테스트 코드로 단정하지 않는다. 검색 품질은 평가에서 확인한다.
- 프롬프트 전문을 스냅샷으로 고정하지 않고 핵심 규칙이 포함됐는지만 확인한다.
