# CB-3-2. 계약 (챗봇 RAG)

> iOS 계약 원본은 `docs/iosapi/apidocs.md §7`. 개편의 대원칙: **API·SSE 계약 무변경** —
> 내부 검색 엔진 교체가 클라이언트에 보이지 않아야 한다. 예외 후보는 아래 결정 2건뿐.

## CB-3-2.0 백엔드 ↔ AI 벤더(OpenAI) — 호출 계약

배치 5기능(`../ai-feature/3-2 §AI-3-2.0`)과 달리 챗봇은 **사용자 질의 시점에 실시간으로**
AI 를 호출한다. 벤더 경계의 호출 종류와 규격:

| 호출 | 시점 | 규격 |
| --- | --- | --- |
| 질문 임베딩 | 질의마다 | `/embeddings` — Spring AI EmbeddingModel(ADR-034), **text-embedding-3-large** — 청크 임베딩과 반드시 동일 모델(같은 벡터 공간이어야 kNN 거리 비교 성립, C-NFR4) |
| 답변 생성 | 질의마다 | `/chat/completions` **비스트림** — (a′) 확정으로 벤더 SSE delta 불요 → ADR-034 제외 사유 해소, Spring AI ChatModel 전환 가능. 시스템+[참고 자료]+히스토리+질문, 자유 텍스트 응답 |
| 재작성·판정 | 질의마다 (답변 생성 후) | 공용 가드레일 어댑터 재사용 — 배치와 동일 규격(판정은 strict `guardrail_verdict`) |
| rerank | 질의마다 | `/chat/completions` — strict json_schema 판정, "확신 없으면 통과" |
| (배치) 컨텍스트 생성 | 색인 시 | ai-feature 규격 그대로 (strict 스키마·temperature 미전송) |

- 공통 계약은 ai-feature 표를 준용: Bearer 인증(NFR-S1)·temperature 미전송(luna 거부)·
  재시도 ADR-014 — 비스트림化로 생성 호출도 배치와 동일하게 재시도 가능해졌다
  (사용자 대기가 늘어나는 만큼 지연 예산 C-NFR1 안에서)
- 배치와의 구조 차이는 "저장 vs 즉시 전송"뿐 — 검증(재작성→판정)이 전송 앞에 오는 것은
  배치와 동일하다(C-FR9 확정). 검증 전 텍스트는 사용자에게 나가지 않는다

## CB-3-2.1 유지되는 계약

- 요청: 클라이언트가 전체 히스토리 + 선택적 맥락(newsId 등) 전송 — 서버 세션 없음
- 응답: SSE 연결 자체는 유지 — 단 본문 델타가 아니라 **진행 단계 이벤트 → 완성 본문 → `source` 이벤트**(§CB-3-2.2 ②). 출처는 청크의 원천(뉴스/용어) 역참조로 구성
- AI 생성 표시·책임 한계 문구 정책 (apidocs §1012)
- 검색 포트 시그니처 유지 → Service·프롬프트 조립 로직 무변경 (CB-3-1.4)

## CB-3-2.2 계약 관련 결정

**① 저근거·0건 응답 (C-FR7 — 확정 9/19)**: rerank 통과 청크 **≤5 = 저근거 모드** — 답변에
"관련 자료가 충분치 않다" 언급을 포함하되 **"자료가 없다"고는 하지 않고** 일반 지식으로 보완.
0건은 동일 규칙의 극단(이때 `source` 빈 목록). 답변 거부는 없다. 현행 "일반 설명 폴백" 계약의
연장이라 **계약 무변경**. 발생 사실은 로그·메트릭·트레이스 기록(0건률·저근거율 급증 = 색인·
검색 점검 신호).

**② SSE 계약 변경 (C-FR9 확정의 귀결 — 계약 확정·apidocs 갱신 완료 9/19)** — 본문 델타
스트림이 **`stage`(generating/refining/verifying) → `answer`(완성 본문) → `source` → `done`**
으로 바뀐다. 검증 실패는 `error → done`(본문 미전송). 확정 계약은 apidocs §7 `POST /chat` 이
원본(개편 배포 전까지 기존 token 계약 병기). 구현 추적: **SCRUM-92(백)·SCRUM-93(iOS)** — 이벤트명이 바뀌므로 동시 배포 필요.
