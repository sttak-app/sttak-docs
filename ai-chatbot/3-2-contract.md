# CB-3-2. 계약 (챗봇 RAG)

> iOS 계약 원본은 `docs/iosapi/apidocs.md §7`. 개편의 대원칙: **API·SSE 계약 무변경** —
> 내부 검색 엔진 교체가 클라이언트에 보이지 않아야 한다. 예외 후보는 아래 결정 2건뿐.

## CB-3-2.0 백엔드 ↔ AI 벤더(OpenAI) — 호출 계약

배치 5기능(`../ai-feature/3-2 §AI-3-2.0`)과 달리 챗봇은 **사용자 질의 시점에 실시간으로**
AI 를 호출한다. 벤더 경계의 호출 종류와 규격:

| 호출 | 시점 | 규격 |
| --- | --- | --- |
| 질문 임베딩 | 질의마다 | `/embeddings` — Spring AI EmbeddingModel(ADR-034), 모델은 ❓C-NFR4 결정 반영 |
| 답변 생성 | 질의마다 | `/chat/completions` **stream=true (SSE)** — 현행 RestClient 어댑터 유지(ADR-034 전환 제외). 시스템+[참고 자료]+히스토리+질문, 구조화 스키마 없음(자유 텍스트 스트림) |
| (채택 시) rerank | 질의마다 | `/chat/completions` — strict json_schema 판정, "확신 없으면 통과" |
| (배치) 컨텍스트 생성 | 색인 시 | ai-feature 규격 그대로 (strict 스키마·temperature 미전송) |

- 공통 계약은 ai-feature 표를 준용: Bearer 인증(NFR-S1)·temperature 미전송(luna 거부)·
  재시도 ADR-014. 단 **스트리밍 생성은 재시도 없음** — 스트림 중단은 SSE 오류로 사용자에
  즉시 노출되는 실시간 경로라, 재시도 대신 오류 계약(§CB-3-2.3)으로 처리
- 배치와의 구조 차이: 배치는 "AI 응답 → 검증 → 저장 → 나중에 조회"지만, 챗봇은 **AI 스트림이
  (가드레일 방식 결정에 따라) 사용자에게 직결**된다 — §CB-4-3 결정이 이 경계의 검증 위치를
  정한다

## CB-3-2.1 유지되는 계약

- 요청: 클라이언트가 전체 히스토리 + 선택적 맥락(newsId 등) 전송 — 서버 세션 없음
- 응답: SSE 스트리밍 + `source` 이벤트(출처 목록) — 출처는 청크의 원천(뉴스/용어) 역참조로 구성
- AI 생성 표시·책임 한계 문구 정책 (apidocs §1012)
- 검색 포트 시그니처 유지 → Service·프롬프트 조립 로직 무변경 (CB-3-1.4)

## CB-3-2.2 결정이 계약에 닿는 것 2건

**① 검색 0건 폴백 (C-FR7)** — 노션 안("관련 기사를 찾지 못했습니다" 안내)은 현행 계약
("자료에 없으면 일반 개념 설명으로 폴백" — ADR-016·apidocs)의 **변경**이다:

| 안 | 사용자 경험 | 계약 영향 |
| --- | --- | --- |
| (a) 일반 지식 답변 + "관련 기사는 찾지 못했다" 부기 | 개념 질문("PER?")도 항상 답을 받음 | 현행 유지 — 무변경 |
| (b) 답변 거부 안내 | 근거 없는 답변 원천 차단 | **계약 변경** — iOS 문구·UX 협의 + 스펙 갱신 세트 |

(b) 채택 시 용어 원천(C-FR2)이 빠지면 개념 질문 전반이 거부되는 사고와 결합함에 유의.
결정을 ADR 에 기록하고 apidocs 동기화.

**② 스트리밍 여부 (C-FR9 와 연동)** — 가드레일 방식에서 (a) 완성 후 일괄 반환을 고르면
SSE 계약 자체가 바뀐다(§CB-4-3). 스트리밍 유지 안을 고르면 계약 무변경.
