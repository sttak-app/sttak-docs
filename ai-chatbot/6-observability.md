# CB-6. 관측성 (챗봇 RAG)

> 체계는 `../ai-feature/6-observability.md` 공유 (Langfuse 트레이스 / 메트릭 / 로그).
> 가드레일 (a′) 확정으로 생성이 비스트림化 → **생성·재작성·판정은 Spring AI 자동 span** 을
> 받는다(ADR-034 제외 사유 해소). 검색 단계(BM25/kNN/RRF/rerank)만 수동 Observation 배선이
> 개편 스코프다. 노션 설계의 로깅 항목이 본 절의 원안이다.

## CB-6.1 트레이스 — 질의 1건의 단계별 기록 (노션 안 확정)

질의당 하나의 트레이스에 단계별 span:

| span | input / output |
| --- | --- |
| query | 사용자 질문 (+ 맥락 newsId) |
| embedding | 질문 임베딩 (모델·토큰) |
| bm25 / knn | 각 검색의 히트 청크 ID·스코어 |
| rrf | 융합 후 순위 |
| rerank | 통과/탈락 청크와 사유 |
| generation | 프롬프트 조립 결과(청크 목록)·출력·토큰 (Spring AI 자동) |
| rewrite / judge | 가드레일 재작성·판정 — 공용 어댑터의 자동 span 그대로 |
| (전체) | 단계별·총 지연 |

- 구현: 수동 Micrometer Observation → 기존 OTel/OTLP 배선 재사용 (신규 인프라 없음)
- 본문 기록 정책 **확정 (9/19)** — ai-feature 와 동일: prod 는 **응답 본문·청크 본문 미기록**
  (메타·청크 ID·스코어는 기록). 단 **사용자 질문(query)은 prod 도 기록** — 0건·저근거 분석과
  검색 품질 개선에 질문 텍스트가 없으면 원인 추적이 불가능해서. 질문은 사용자 입력이므로
  개인정보가 섞일 수 있음을 인지하고, 문제 시 마스킹·기록 중단을 검토
- 샘플링 **전수(1.0)로 시작 (9/19)** — 배치는 일 물량이 고정이라 전수가 당연했지만, 챗봇은
  사용자 트래픽에 비례해 트레이스 양·Langfuse 비용이 가변이다. 그래서 전수로 시작하되
  **출시 후 실제 트래픽 기준 비용을 확인하고**, 과다하면 그때 샘플링 비율(`LANGFUSE_TRACING_
  SAMPLING`)을 내린다 — 지금 비율을 정하는 게 아니라 확인 절차를 정하는 것
