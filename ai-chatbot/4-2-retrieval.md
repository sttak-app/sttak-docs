# CB-4-2. 구현: 검색 (구현 예정)

`3-1`에서 설명한 질의 파이프라인(BM25·벡터 검색 → RRF → rerank)의 구현 계획이다.
아래 값은 설계 과정에서 정한 초깃값이며, 평가(`4-4`) 결과에 따라 설정으로 조정한다.

## CB-4-2.1 검색 흐름

```
질문 → 질문 임베딩 (text-embedding-3-large, 청크와 동일한 모델)
     → ① BM25 (search_text, nori, k=30) ┐  둘 다 공통 필터: stock_codes / published_at ≥ 최근 7일
     → ② kNN (embedding, cosine, k=30)  ┴→ ③ RRF(k=60) 융합 상위 30
     → ④ rerank (관련성 필터) → 통과한 0~30개를 프롬프트에 입력
```

## CB-4-2.2 확정한 구현 값과 근거

| 항목 | 확정 | 근거 |
| --- | --- | --- |
| 후보 수 | BM25 최대 30개, kNN 최대 30개. 양쪽 모두 결과가 없을 수도 있다 | 검색 대상이 최근 7일의 수천 개 청크이므로 리콜을 확보하기에 충분하며, 일반적인 top-k 범위에도 들어간다 |
| RRF 상수 | k=60으로 직접 구현하고 상위 30개를 선택한다 | 널리 쓰이는 값이며 수식이 단순해 라이브러리나 검색 엔진의 자체 기능 없이 코드로 계산할 수 있다. 현재 데이터 규모에서는 별도로 조정해도 얻을 수 있는 효과가 크지 않다 |
| 기간 필터 | **최근 7일 고정**. 용어(TERM) 청크와 NEWS 승격은 예외 | 전체 데이터는 색인에 보존하고 검색할 때만 필터를 적용해 기간을 설정으로 바꿀 수 있게 한다 |
| kNN 필터 방식 | **pre-filter**. 필터 조건에 맞는 청크 가운데 가장 가까운 30개를 선택한다(kNN 질의의 `filter` 파라미터) | post-filter를 사용하면 먼저 선택한 30개가 모두 제외되어 검색 결과가 없을 수 있다 |
| 용어 검색 | 같은 인덱스에서 `source_type=TERM`인 문서도 함께 조회한다 | 별도의 질의와 결과 병합 로직이 필요 없다(`4-1`) |
| 프롬프트 투입 수 | rerank를 통과한 0~30개를 그대로 사용한다. NEWS 승격 청크는 별도로 추가한다 | 검색 청크 30개를 모두 넣어도 프롬프트 예산 안에 들어가며, 남길 개수는 rerank가 결정한다 |
| 점수 임계값 | 사용하지 않음 | 데이터가 적어 질문마다 점수 분포가 크게 달라지므로 고정 기준을 정하기 어렵다 |

## CB-4-2.3 rerank 구현 방식

- RRF 상위 후보 전체를 **한 번의 LLM 호출**로 판정한다. strict `json_schema`로 청크별
  관련 여부를 받으며, 청크마다 따로 호출하지 않는다. rerank는 답변 생성 전에 순차적으로
  실행되므로 호출 횟수가 늘면 사용자의 대기 시간도 바로 늘어난다.
- 관련성을 확신하기 어려우면 해당 청크를 통과시켜 지나친 제외를 막는다. 모든 청크가
  제외되면 일반 지식으로 답한다(C-FR6).
- 판정할 수 없으면 전체 후보를 통과시킨다(fail-open, `5-2`). 입력에 없던 청크가 결과에
  추가될 수는 없다(`3-2`).
- 판정 프롬프트 문안·통과 기준·지연 영향(NFR2 예산 내)은 평가로 확정한다.
- 토큰은 `job=chat-rerank`로 집계한다(`6`).

## CB-4-2.4 기존 코드에 적용하는 방식

- **검색 포트의 시그니처는 유지한다.** 현재 챗 서비스의 RAG 검색 및 프롬프트 조립 호출부는
  그대로 두고, 포트 구현만 하이브리드 검색 어댑터로 교체한다.
- 프레임워크의 `VectorStore` 추상화는 BM25와 RRF를 지원하지 않으므로 **검색 엔진
  클라이언트를 직접 사용한다.** 색인용 포트는 검색 포트와 분리해 새로 만든다.
- `sttak.rag.store=pgvector|es` 설정으로 검색 구현을 전환한다. 전환 기간에는 양쪽에 모두
  색인하고 검색 경로만 설정으로 선택한다(`7`). 안정화가 끝나면 기존 경로와 설정을 함께
  제거한다.
- **NEWS 승격**(C-FR5): `newsId`에 해당하는 청크는 검색 결과와 관계없이 첫 번째 참고
  자료로 올리며 기간 필터도 적용하지 않는다. 현재 동작을 유지한다.
- 통과한 문서의 `source_url`은 그대로 생성 입력에 전달한다(`3-2` 원칙 6). 검색 과정에서
  URL을 제거하는 변환은 두지 않는다.

## CB-4-2.5 검색 결과가 없을 때의 처리

어느 단계에서든 검색 결과가 없다는 이유만으로 실패 처리하지 않는다(C-FR1). 검색 호출
자체가 실패한 장애와는 구분하며, 장애 상황은 `5-2`에서 다룬다.

| 상황 | 처리 |
| --- | --- |
| BM25와 벡터 검색 중 **한쪽에만 결과가 있는 경우** | 합칠 순위가 없으므로 RRF를 생략하고 **결과가 있는 쪽의 목록을 그대로 rerank에 전달한다** |
| **양쪽 모두 결과가 없는 경우** | 판정할 후보가 없으므로 RRF와 rerank를 생략한다. NEWS 승격 청크도 없으면 일반 지식 답변을 생성한다(C-FR6) |
| rerank를 통과한 청크가 없는 경우 | NEWS 승격 청크가 있으면 해당 청크를 참고 자료로 사용한다. 승격 청크도 없으면 일반 지식 답변을 생성한다(C-FR6) |

- NEWS 승격(C-FR5)은 검색 결과와 관계없이 적용한다. 양쪽 검색 결과가 없어도 승격 청크가
  있으면 해당 청크로 [참고 자료]를 구성하므로 0건 경로에 해당하지 않는다.
- 결과가 없었던 단계는 로그와 메트릭에 남긴다(`6`). 발생 비율이 갑자기 높아지면 색인과
  검색 상태를 점검한다.
