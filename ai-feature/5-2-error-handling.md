# AF-5-2. 에러 처리 (배치 AI 기능)

예외 계층과 HTTP 매핑은 `../5-2-error-handling.md`를 따른다. 이 문서에서는 배치 AI 작업
중 발생한 실패를 어디까지 처리하고, 어떤 작업을 계속 진행할지 정한다.

## AF-5-2.1 실패 시 통과(fail-open)와 차단(fail-closed)의 경계

| 상황 | 방향 | 이유 |
| --- | --- | --- |
| 검수 호출 또는 응답 파싱 실패 | **통과**(fail-open) | 검증 시스템의 장애로 정상 콘텐츠를 막는 피해가 더 크다. 정상 평가셋에서 오탐이 없었던 결과도 함께 고려했다 |
| 검수 refusal(응답 거부) | **반려**(fail-closed) | 단순히 판단이 어려운 상황이 아니라 입력 이상 신호로 본다. 재생성 실패와 검수 불능이 겹쳐 검증하지 않은 원문이 저장되는 경로를 막는다 |
| 재생성 호출 실패 | 원문을 유지하고 검수 진행 | 검수가 마지막 차단 단계 역할을 한다 |
| 잠금 값 위반 | **반려** | 표현을 다듬는 과정에서 구조화된 값이 바뀌면 데이터가 오염되므로 저장하지 않는다 |

## AF-5-2.2 상황별 처리

| 상황 | 처리 | 이유 |
| --- | --- | --- |
| 생성 호출 실패(429/5xx·타임아웃) | `SpringAiRetrySupport`가 지수 백오프로 최대 3회 다시 시도한다. 4xx 응답은 즉시 실패시키며, 재시도 횟수를 모두 사용하면 해당 건만 실패로 처리한다 | AI 제공자의 일시적인 장애가 배치 전체를 중단시키면 안 된다. 프레임워크 기본값인 10회·3분 재시도는 지나치게 길어 사용하지 않는다 |
| 응답 형식 오류(내용 없음·잘못된 JSON) | 해당 건 실패 | 저장할 수 없는 결과다 |
| 가드레일 재시도 소진 | 해당 건 실패 + 소진 카운터 증가 | 위반이 남은 콘텐츠는 저장하지 않는다 |
| 시스템 장애(메모리 고갈 등) | 처리하지 않고 작업 실패 | 즉시 경보가 필요한 시스템 문제이므로 개별 데이터의 실패와 구분한다 |

## AF-5-2.3 구현된 기능별 실패 처리

| 기능 | 예외 | 실패 시 | 사용자에게 보이는 것 |
| --- | --- | --- | --- |
| 퀴즈 | `QuizException.QUIZ_GENERATION_FAILED` | 해당 문항을 버리고 최대 3회 다시 생성 | 해당 회차의 문항 수가 줄어들 수 있음 |
| 차트 해설 | `ChartException.EXPLANATION_GENERATION_FAILED` | 저장하지 않고 anti-join을 통해 다음 배치에서 다시 처리 | 해설 대신 정해진 안내 문구 표시(`explanation: null`) |
| 회고 | `TradeException.REVIEW_GENERATION_FAILED` | 저장하지 않고 다음 정산 배치에서 다시 처리 | 회고 대기 상태 |

모든 기능이 기존 예외 enum을 사용하므로 새로운 ErrorType이나 HTTP 매핑은 추가하지 않는다.
`Exception` 계열의 오류만 건별로 처리한다. OOM 같은 `Error`나 프레임워크 장애는 배치 작업
전체를 실패시켜 경보가 발생하게 한다.

이러한 실패는 사용자 조회 요청의 오류로 이어지지 않는다. 생성된 결과가 없으면 해당 내용을
제외하거나 대기 상태로 보여 준다.

## AF-5-2.4 격리 규약

1. **건별 격리**: 한 건이 실패해도 같은 회차의 다른 건은 계속 처리한다. 저장은 건별
   트랜잭션(REQUIRES_NEW 또는 리포지토리 자체 트랜잭션)으로 분리한다.
2. **단계별 격리**: 생성 단계 전체가 실패해도 앞에서 완료한 수집·감지·정산 결과는 되돌리지
   않는다.
3. **중복 격리**: 배치를 다시 실행해 중복 충돌이 발생하면 이미 처리된 것으로 보고 넘어간다.
4. **반복 실패 관리**: 오래된 데이터부터 처리하므로 같은 건이 계속 실패하면 매 회차 앞에서
   처리량을 차지할 수 있다. 이런 사례가 발생하면 건별 재시도 횟수를 기록하는 방안을 검토한다.

## AF-5-2.5 로그 규약

- 실패 로그에는 대상 ID와 실패 원인을 중심으로 남긴다. 생성된 콘텐츠 전체를 기록하지 않고,
  위반 문장이 필요할 때도 짧은 인용만 남긴다.
- API 키·인증 헤더는 어떤 로그·예외 메시지에도 싣지 않는다.
- 재시도 횟수 소진은 정해진 대체 처리가 동작한 경우이므로 `warn`으로 기록한다. `error`는
  작업 자체가 중단되는 상황에만 사용한다.
