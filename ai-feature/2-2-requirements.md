# AF-2-2. 요구사항 (배치 AI 기능)

각 기능은 해결하려는 문제, 입력, 출력, 필수 규칙 순서로 설명한다. 유사도 기준값, 재시도
횟수, 한 번에 생성할 수 있는 양과 같은 세부 값은 이 문서에서 고정하지 않는다. 평가와 운영
결과를 바탕으로 정하고 설정으로 조정한다.

## AF-2-2.1 기능 ① 학습 퀴즈 생성

**해결하려는 문제**: 기존 문항과 겹치지 않는 기초 개념 학습 콘텐츠를 지속해서 제공한다.

| 구분 | 내용 |
| --- | --- |
| 입력 | 별도 원본 데이터 없이 주제 범위를 지정한 프롬프트만 사용 |
| 출력 | 문항 + 선지 4개 + 정답 번호 + 2~3문장 해설 |

정확한 필드명과 출력 예시는 `3-2-contract.md`의 [퀴즈 생성 계약](./3-2-contract.md#af-3-21-퀴즈-생성)을 따른다.

**규칙 (Q-FR)**

| ID | 요구사항 |
| --- | --- |
| Q-FR1 | 개념, 정의, 원리만 다룬다. 시황, 전망, 특정 종목은 언급하지 않는다. |
| Q-FR2 | 정답은 유일하고, 오답은 그럴듯하며, 선지 길이는 균형이다. |
| Q-FR3 | 임베딩 유사도를 기준으로 기존 문항과 의미가 겹치면 폐기하고 다시 생성한다. 재생성 횟수에는 상한을 둔다. |
| Q-FR4 | 검증(재생성) 과정에서 정답 번호(`correctChoice`)가 바뀌지 않도록 코드로 잠근다. |

## AF-2-2.2 기능 ② 차트 신호 해설

**해결하려는 문제**: 서버가 감지한 기술적 신호를 초보자도 이해할 수 있게 설명한다. 이때
사용자가 해당 신호를 매매 시점에 대한 조언으로 받아들이지 않도록 주의한다.

| 구분 | 내용 |
| --- | --- |
| 입력 | 감지된 신호 1건: 신호 종류 + 종목 + 발생 시점 + **고정 설명문**(미리 작성한 감지 조건 설명) |
| 출력 | 4~5문장 해설: ① 신호의 의미 ② 발생 원리 ③ 이번 발생 맥락 ④ 반대 해석 가능성 |

정확한 필드명과 출력 예시는 `3-2-contract.md`의 [차트 신호 해설 계약](./3-2-contract.md#af-3-22-차트-신호-해설)을 따른다.

**규칙 (S-FR)**

| ID | 요구사항 |
| --- | --- |
| S-FR1 | 감지에 실제 사용한 파라미터, 즉 고정 설명문에 있는 내용만 언급한다. 모델이 감지 조건을 임의로 만들면 안 된다. |
| S-FR2 | 주가 방향을 단정하지 않고 "~로 해석되곤 해요"처럼 가능성을 설명한다. 결과에 맞춰 해설하는 일을 막기 위해 신호 발생 후의 실제 주가 방향은 입력하지 않는다. |
| S-FR3 | 신호 하나에 해설 하나만 생성하며, 생성한 해설은 바꾸지 않는다. 같은 신호의 해설을 다시 생성하지 않는다. |

## AF-2-2.3 기능 ③ 매매 회고

**해결하려는 문제**: 사용자가 모의 매매의 손익만 확인하고 끝내지 않고, 자신의 판단 과정을
돌아보게 한다. 평가 대상은 결과가 아니라 사용자가 작성한 매매 근거다.

| 구분 | 내용 |
| --- | --- |
| 입력 | 정산된 매매 1건: 종목 + 매수/매도 정보 + 손익 + **매매 근거(rationale, 사용자가 작성한 자유 형식 텍스트)** |
| 출력 | 한 줄 총평 + 잘한 점 + 점검 질문과 학습 주제 + 매매 근거 평가 1~3개(GOOD/BAD/IMPROVEMENT) |

정확한 필드명과 출력 예시는 `3-2-contract.md`의 [매매 회고 계약](./3-2-contract.md#af-3-23-매매-회고)을 따른다.

**규칙 (R-FR)**

| ID | 요구사항 |
| --- | --- |
| R-FR1 | 핵심 평가 대상은 `rationale`이다. 손익이 아니라 사용자의 판단 과정을 다룬다. |
| R-FR2 | 잘한 점을 억지로 만들지 않는다. 아쉬운 점은 지적이 아니라 점검 질문 + 학습 주제 형태다. |
| R-FR3 | `rationale`은 사용자가 작성한 입력이므로 프롬프트 주입 방어를 거친다. 검수 단계에서 발생한 refusal은 통과로 보지 않고 반려한다. |
| R-FR4 | 검증(재생성) 과정에서 `evaluations`의 개수와 타입 순서가 바뀌지 않도록 코드로 잠근다. |
| R-FR5 | 정산된 거래마다 회고 하나만 생성하며, 생성한 회고는 수정하지 않는다. |

## AF-2-2.4 공통 규칙 (G-FR)

| ID | 요구사항 |
| --- | --- |
| G-FR1 | 모든 결과물은 저장 전에 가드레일을 거친다. 항상 한 번 재생성한 뒤 후보 탐지 힌트를 포함해 검수하고, 위반이 있으면 피드백을 반영해 다시 생성한다. 재시도 상한 안에 검수를 통과한 결과만 저장하며, 횟수를 모두 소진하면 저장하지 않는다. `../ai-chatbot/`의 G-FR1과 같은 파이프라인이다. |
| G-FR2 | 위반 범주와 위반으로 보지 않을 사례(교육 목적의 언급, 부정 문맥, 인용, 사실 보도)를 검증 자산으로 관리한다. 목록을 바꾸면 평가셋을 다시 검증한다. |
| G-FR3 | 생성에 실패하거나 검증 횟수를 소진해도 해당 건만 실패로 처리하고 배치·수집·정산은 계속 진행한다. 실패한 건은 다음 배치에서 다시 생성한다(멱등 재생성). |

## AF-2-2.5 비기능 요구사항 (NFR)

| ID | 요구사항 |
| --- | --- |
| NFR1 | 모든 콘텐츠는 배치(경로 B)에서 생성한다. 조회할 때는 LLM을 호출하지 않는다. |
| NFR2 | 비용과 부하를 분리하기 위해 한 번에 생성할 수 있는 양에 상한을 둔다. 백필이 필요하면 설정값을 높여 한 번에 처리한다. |
| NFR3 | 프롬프트는 검증 대상 자산으로 관리하며, 수정하면 평가셋을 다시 검증한다. |
| NFR4 | 토큰 사용량을 기능과 검증 단계별로 나누어 기록한다. 자세한 내용은 `6-observability`에서 다룬다. |
| NFR5 | API 키는 환경 변수나 시크릿 저장소를 통해서만 주입하고, 로그·커밋·예외 메시지에 노출하지 않는다. |
